質問にこたえると、16タイプのうちどれに近いかを AI が返す診断を作って、本番に出した。

https://poina.petit-bouquet.com

使ったのは **Jev**。2026年9月に出たばかりの、**文章を書かないAI** だ。テキストを生成せず、渡した選択肢に対する**確率だけ**を返す。

この記事で書くのは3つ。

- **画面を作る前に、確率分布のほうを先に確かめた話**（要件がそこに乗っていたので）
- **Workers AI 経由だと応答が `result` で包まれて返る**、という地味に効く罠
- **題材の商標を、名前を決める前に調べた記録**

「触ってみた」で終わらせずに、**本番に載せて運用の形にするまで**に何が要ったかを書く。

## Jev とは何で、なぜこの題材なのか

Jev は TypeSafe AI が 2026年9月16日に公開したモデルで、**テキストを出力しない**。

やることは1つだけだ。**「状態」と「質問」を渡すと、答えを型つきで返す。** 質問には3種類ある。

| 種類 | 返すもの |
| --- | --- |
| `choice` | 選択肢のどれか ＋ **全選択肢の確率分布** |
| `score` | 評価基準に沿ったスコア |
| `noul` | 真偽（0〜1の確率） |

何が嬉しいかは、一言でいうとこうなる。

:::message
**出力の形が崩れない。** 生成ではないので `JSON.parse` に失敗しないし、
「余計な前置きを書かないでください」とプロンプトでお願いする必要もない。
:::

LLM に構造化出力をさせて、たまに返ってくる ```` ```json ```` つきのレスポンスをパースし損ねた経験があるなら、この一点だけで刺さると思う。

### なぜ性格診断だったか

Jev は **if 文と LLM のあいだを埋める道具**だと説明されている。裏を返すと、**題材が「分類」の形をしていないと嬉しさが出ない。**

16タイプの性格分類は、そこにぴったりはまった。

- 選択肢が **16個で固定**
- 欲しいのは「どれか1つ」ではなく **「どれにどれくらい近いか」**
- `choice` は **最大255個**まで選択肢を取れるので、16個は1回で投げきれる

実際に投げるリクエストはこれだけだ。

```ts
{
  state: {
    説明: '性格についての設問に、0〜100 で答えたもの。',
    回答: [
      { 設問: '知らない人が多い集まりでも、わりと平気で話しかけにいく。', 目盛り: 20, 意味: 'あまりそう思わない' },
      // …
    ],
  },
  questions: {
    type: {
      type: 'choice',
      instructions: 'この回答をした人は、16タイプのうちどれにいちばん近いか。',
      criteria: {
        INTJ: 'ひとりの時間で元気が戻り…（略）',
        INTP: '…',
        // 16個
      },
    },
  },
}
```

返ってくるのはこう。

```json
{
  "choice": "INFP",
  "confidence": 0.68,
  "probabilities": { "INFP": 0.70, "INFJ": 0.24, "INTP": 0.03, "ISFP": 0.01, "...": 0 }
}
```

**`probabilities` が16件ぶん、合計 1.0 で返る。** このサイトが欲しかったのは1位ではなく、この分布そのものだった。

## 画面を作る前に、確率分布のほうを確かめた

ここがこの記事の本題。

### 要件が「分布の形」に乗っていた

作るものの要件に、こういう1行があった。

> 他に可能性の高いタイプとして2番目・3番目も参考程度に表示

素直に読めば「返ってきた確率を降順に並べて上位3件を出す」だけだ。でも、**ここには前提がある。**

:::message alert
**1位に全振りした分布しか返らないなら、この要件は丸ごと成立しない。**
2位が 0.1%、3位が 0.05% では「参考程度に表示」する意味がない。
:::

そして、それが起きるかどうかは**投げてみないと分からない。** 性格診断は正解のない主観タスクで、モデルがどれくらい自信を持って answer するかは、事前に読めない。

画面を全部作ったあとに「分布が使い物にならないので判定方式を作り直します」になると高い。**先に測った。**

### 4種類の回答を投げた

ダミーの回答セットを作って、分布の形だけを見る小さなスクリプトを書いた。

```ts
/** 指定した4文字に寄せた回答を作る。設問の向きに合わせて振る */
function leaning(code: string, mode: Mode, strength = 40): Answers {
  const letters = new Set(code.split(''))
  const a: Answers = {}
  for (const q of questionsFor(mode)) {
    a[q.id] = letters.has(q.pole) ? 50 + strength : 50 - strength
  }
  return a
}

/** 分布の散らばり。1 に近いほど平ら、0 に近いほど1点に集中 */
function normalisedEntropy(ps: number[]): number {
  const s = ps.reduce((x, y) => x + y, 0)
  let h = 0
  for (const p of ps) {
    const q = p / s
    if (q > 0) h -= q * Math.log(q)
  }
  return h / Math.log(ps.length)
}
```

結果。

| 投げたもの | 1位 | 2位 | 3位 | 散らばり |
| --- | --- | --- | --- | --- |
| はっきり INTJ に寄せた（±40） | INTJ 96% | ISTJ 2% | INTP 2% | 0.071 |
| はっきり ESFP に寄せた（±40） | ESFP 61% | ESFJ 26% | ESTP 9% | 0.375 |
| ゆるく INFP に寄せた（±15） | INFP 73% | INFJ 18% | INTP 6% | 0.300 |
| 全部まんなか（50） | INTP 51% | ISTJ 19% | INTJ 7% | 0.589 |

**乗っていた。**

- 極端に寄せれば尖り（散らばり 0.071）、曖昧にすれば平らになる（0.589）
- **人間が実際にやる「ゆるく寄った」回答**で、2位 18% / 3位 6% と意味のある数字が出る

これを見て、**16択を1回投げる形で確定**した。4指標（E/I・S/N・T/F・J/P）を `score` で4本取って合成する案は見送っている。

:::message
**見送りの理由は「分ける必要が無かった」だけ**なので、分布が壊れたらこの案は戻ってくる。
そう書いてリポジトリに残してある。**却下ではなく保留**として扱いたかった。
:::

### 一般化できる話として

これは Jev に限らない。

**LLM でも同じことが言える。** 出力の「形」（スキーマに合うか）ではなく **「性質」**（分布・ばらつき・境界でのふるまい）に要件が乗っているなら、**UI を作る前にそこを測る。**

スキーマは型で守れるが、**分布は型で守れない。** そして分布が要件を満たさないと分かったときの手戻りは、だいたいアーキテクチャまで届く。

## 実装 —— Cloudflare Workers から呼ぶ

Jev は Cloudflare Workers AI が公式モデルとして持っているので、**TypeSafe の API キーを自分で持たなくていい。**

```ts
const res = await env.AI.run('typesafe/jev', {
  state,
  questions,
}, { gateway: { id: 'poina' } })
```

バインディングを1行足すだけ。

```jsonc
// wrangler.jsonc
"ai": { "binding": "AI" }
```

### 応答が `result` で包まれて返る

ここで **5回続けて 502 を出した。**

```
X [ERROR] judge failed: 判定モデルが確率を返さなかった
[wrangler:info] POST /api/judge 502 Bad Gateway (285ms)
```

生の応答をログに落として、やっと分かった。

```json
{
  "state": "Completed",
  "result": {
    "model": "jev-1.13.0",
    "answers": { "type": { "choice": "ENTJ", "probabilities": { ... }, "confidence": 0.85 } },
    "usage": { "input_tokens": 3041, "output_tokens": 149 }
  }
}
```

**Workers AI 経由だと、応答が `result` で包まれて返る。** TypeSafe の API を直に叩いたときは包まれない。ドキュメントのサンプルは後者の形で書かれていることが多いので、そのまま `res.answers` を読みにいくと `undefined` になる。

:::message alert
**いちばん厄介なのは、モデルが正しく答えていること。**
285ms で `ENTJ 0.87` という妥当な答えが返ってきているのに、こちら側で読めていないだけ。
**「モデルが変な答えを返している」と思って調べにいくと、時間を落とす。**
:::

両方の形で読めるようにした。

```ts
const env = raw as { result?: unknown }
const res = (env?.result ?? raw) as {
  answers?: { type?: JevChoiceAnswer }
}
```

### コストと速さ

実測値。おためしモード（10問）で1回判定したときの数字。

| | |
| --- | --- |
| 入力トークン | **3,041** |
| 出力トークン | 149（**課金対象外**） |
| 料金 | $0.042 / 1M トークン → **約 $0.00013 / 回** |
| 応答 | **290〜320ms**（コールドスタートの初回のみ 1.2 秒） |
| 本番での1発目 | 1,312ms / confidence 0.68 |

16タイプぶんの判定基準文を毎回投げているので入力は3,000トークンを超えるが、**それでも1回あたり 0.02円**に届かない。実質ゼロだが、無料ではない。`wrangler dev` でも本物を叩くので、手元で試しても課金される点は頭の片隅に置いておきたい。

## 「回答を保存しない」を最後まで通す

性格診断は**他人の内面を預かる。** 持たなければ漏れないので、最初にこう決めた。

- サーバに保存しない
- 結果ページの URL にも残さない
- アクセス解析も入れない

ここで1つ落とし穴があった。

:::message alert
**AI Gateway は既定でリクエストとレスポンスを記録する。**
通したまま何もしないと、**利用者の回答内容がゲートウェイのログに溜まる。**
:::

ダッシュボードで Log requests を off にした。さらに、**手元の開発では `.dev.vars` でゲートウェイ自体を迂回**している。通したままだと、開発中に自分が投げた回答がログに混ざるからだ。

```bash
# .dev.vars（git には入らない）
AI_GATEWAY_ID=
```

本番は `wrangler.jsonc` の値（`poina`）を使い、手元だけ空にして直に叩く。**本番の設定を汚さずに手元だけ外せる。**

### 結果ページを「保存せずに」作る

要件にこういうものがあった。

> 結果発表ページは同じURLであれば、誰が見ても同じ中身が表示される
> 2番め・3番めについては、クエリパラメータで変化させるためシェアURLから遷移した場合には表示されない

これを**サーバに何も保存せずに**満たしたい。やったのはこう。

| URL | 見えるもの |
| --- | --- |
| `/result/04` | そのタイプの説明だけ（誰が開いても同じ） |
| `/result/04?p=70.0&s=03&sp=24.0&t=02&tp=3.0` | **確率と2位・3位つき** |

**確率は、診断した本人の数字だ。** 共有された URL から来た人に出すと、その人のものではない数字を自分のものとして読むことになる。だから**クエリパラメータでだけ渡す。**

シェアボタンが作る URL にはクエリを付けていないので、**共有された先では確率も2位・3位も出ない。** DB もセッションも要らない。

:::message
**行き先の URL はサーバ側の1箇所だけで組み立てている。**
`POST /api/judge` が `to`（行き先そのもの）を返し、画面側はそこへ飛ぶだけ。
画面側でも組み立てると、クエリの形が2箇所になって必ずズレる。
:::

あと、結果ページを `/result/INTJ` ではなく **`/result/01` 〜 `/result/16`** にしているが、これには理由がある。次の章につながる。

## 題材の商標を、名前を決める前に調べた

16タイプの性格分類は、**先行する商標と著作物がある題材**だ。作り始める前に一度だけ調べた。

:::message alert
以下は法的な助言ではない。**個人の技術検証サイトを公開する範囲で、踏みそうな地雷を自分で見にいった記録**であって、それ以上のものではない。商用展開まで視野に入れるなら弁理士に相談したほうがいい。
:::

調べたのは3点。

### 1. あの4文字の代名詞になっている名前を名乗れるか → 名乗れない

日本での登録商標を引いた。

| 登録番号 | 権利者 | 区分 |
| --- | --- | --- |
| 第5292740号 | エムビーティーアイトラストインコーポレーテッド | **16・35・41・44類** |

**第41類は「教育・娯楽・スポーツ・文化」。** Web 上の性格診断サービスは、まさにこの区分に入る。避けようがないので、**名乗らない**で確定した。

ここで1つ助かったことがある。**リポジトリ名を `jev-mbti` にしかけて、リポジトリを作る直前に気づいた。** 作ったあとだったら、名前を変えるのは面倒だった。

なお「Myers-Briggs Type Indicator および MBTI は Myers & Briggs Foundation の商標です」という**打ち消しの一文**は、事実の記述なのでサイトに1箇所だけ置いている。

### 2. 「16タイプ」と書けるか → 書ける

権利者側が公表している商標一覧に `16 types` や `16 personality types` は含まれていない。個別の4文字コード（`INTJ` など）も含まれていない。

ただし J-PlatPat で「16タイプ」を含む登録を引いたら、こうだった。

| 商標 |
| --- |
| １６タイプ・パーソナルカラー |
| １６タイプ恋愛診断 |
| １６タイプ性癖診断 |

**どれも「16タイプ＋用途」の複合。** 裏を返すと、**「16タイプ」だけでは識別力が足りず、単体では登録されていない。** 一般的な説明語として書くぶんには問題ない。

なので、こう決めた。

- **サービス名は独自に立てる**（このサイトは「ぽいな性格診断」）
- **「16タイプ」は説明コピーの中だけで使う**
- ★ **「16タイプ＋用途」の形をサービス名にしない** ★

`/result/INTJ` ではなく `/result/01` にしたのも同じ流れで、**共有される URL に4文字コードを出さない**ためだ。

### 3. 既成のタイプ説明文を流用できるか → できるものが無い

ここがいちばん意外だった。候補を1つずつ潰した結果、**そのまま使える説明文はひとつも無かった。**

| 候補 | 判定 | 理由 |
| --- | --- | --- |
| 有名な無料診断サイトの解説文 | ❌ | 利用規約で `reproduce, translate` を明示的に禁止 |
| 同・タイプ愛称（日本語） | ❌ | **日本語の愛称そのものが、そのサイトの翻訳成果物** |
| 公式の解説書 | ❌ | 著作権 ＋ 名称自体が商標 |
| ユング『心理学的類型』の原文 | ❌ | **没後70年 → 2031年末まで保護。PD ではない** |
| Wikipedia | △ | CC BY-SA 4.0。**継承義務**がサイト文章に付く |

一方で、**4指標（E/I・S/N・T/F・J/P）とその組み合わせという「理論・アイデア」は自由に使える。** アイデアは著作権の保護対象外なので、特定の表現を写さない限り問題ない。

そこで、**16タイプの愛称・説明文・設問30問を全部書き下ろした。**

```ts
{
  no: '04', code: 'INFP', nickname: '内に灯をともすひと',
  lead: '「これは違う」に、静かに正直。',
  body: '自分のなかの「これは違う」「これは好き」に正直。大きく主張しないが、価値観に反することは受け入れないこだわりがある。…',
  note: '自分の価値観に合うかどうかが行動の基準で、外からの基準では動きにくい',
}
```

### 制約が、そのまま設計になった

書き下ろすと決めたあとで気づいたのだが、**これは制約というより都合が良かった。**

Jev に渡す `criteria`（各タイプの判定基準文）は、結局「そのタイプはどういう人か」を書いたものだ。つまり **サイトに出す説明文と、モデルに渡す判定基準は、ほぼ同じもの**になる。

実際、`criteria` は4指標の文を組み立てて生成している。

```ts
export const AXIS_TEXT: Record<string, string> = {
  I: 'ひとりの時間で元気が戻り、考えを内側でまとめてから出す',
  E: '人と関わることで元気が出て、話しながら考えがまとまる',
  N: '可能性・意味・この先どうなるかのほうに目がいく',
  // …
}

export function criteriaOf(t: TypeEntry): string {
  const axes = t.code.split('').map((l) => AXIS_TEXT[l]).join('。')
  return `${axes}。${t.note}。`
}
```

16個を手で書くと軸の説明が少しずつズレるが、**組み立てにすればズレようがない。**

**説明文を書く作業と、判定精度を詰める作業が同じものになった。** もし既成の説明文を引いてきていたら、この一致は起きなかった。

## 出す前の点検を「一本道」にした

素の `wrangler deploy` は使わず、`npm run release` から出すようにしている。点検に入れるかどうかの基準は1つだけにした。

> **画面を見ただけでは気づけないものだけを見る。**

画面を開けば分かることは点検しない。**怖いのは「200 が返っていて、見た目も正常で、でも壊れている」状態**だから。

| 見ているもの | 気づけない理由 |
| --- | --- |
| 商標の語が打ち消し文以外に無いか | **文字列ひとつで「名乗った」ことになる。混ざっても普通に動く** |
| OGP 画像が17枚そろっているか | **SNS に貼るまで気づけない** |
| Web フォントが引けるか | **引けなくても画面は出る。別の字で出るだけ** |
| `noindex` の混入 | 別プロジェクトから設定を写すと紛れ込み、**検索から消える** |
| 回答内容をログに出していないか | 「保存しない」と矛盾するが、動きは変わらない |

```
── 出す前の点検 ──

  [ok] 他サービス由来の呼称なし
  [ok] OGP 17枚そろっている
  [ok] noindex / Disallow の混入なし
  [ok] 書体が引けて、ウェイトは 400 だけ
  [ok] 回答内容はログに出していない
  [ok] コントラスト比は全部 4.5 以上
  [ok] 秘密になりうるファイルは git に入っていない

点検はぜんぶ通った。
```

### 点検を足したら、わざと壊して止まることを見る

**緑になっただけでは、網が張れているか分からない。** 4通り壊して確かめた。

| 壊し方 | 結果 |
| --- | --- |
| 商標の語を1つ混ぜた | 止まった |
| `noindex` を混ぜた | 止まった |
| OGP を1枚隠した | 止まった |
| 観測ログの設定を on に戻した | 止まった |
| 全部もどした | **止まらなくなった** |

### 点検が、自分の書いたコメントに反応して止まった

笑い話だが、実害がある。

`noindex` の混入を見る点検を足したら、ソースにこう書いたコメントに反応して止まった。

```ts
/* ★ 別プロジェクトの robots.txt を写さないこと。noindex が紛れると検索から消える ★ */
```

**中身は正しいのに止まる点検は、そのうち無視される。** それがいちばんまずい。配信されるものを見る点検は、**コメントを落としてから見る**ようにした。

:::message
**この型、同じ日に3回踏んだ。**
「共有 URL に2位・3位が出ていないか」の動作確認も、**ページの説明文に出てくる同じ語句**を拾って誤検出した。
**文字列で探すときは、探す対象を構造で絞る。** 「その語を含むか」ではなく「`<h2>その語</h2>` があるか」で数える。
:::

## 見た目は「数で見ないと分からない」

最後に、**画面は普通に出ているのに壊れていた**ものを並べる。どれも目視では見つからなかった。

| 症状 | 数字 | なぜ見ても分からないか |
| --- | --- | --- |
| タイプの記号のコントラスト不足 | **4.14**（本文基準 4.5） | 見た目では判断できない。計算して見つけた |
| 1問目で「ひとつもどる」が見えている | `hidden` なのに `.btn` の `display: block` が勝つ | **押しても何も起きない死んだボタン**にしか見えない |
| フッターの下に本文が潜る | 実寸 **105px** vs 逃がした量 **84px** | **スクロールすれば読めてしまう** |
| 濃紺のバーの上でフォーカス枠が沈む | **1.77** | Tab で辿ると、そこだけ枠が消えたように見える |
| リンクの当たり判定が縦に重なる | **6px** | 押し間違えるまで分からない |
| 設問ごとに本文の箱の幅が変わる | 横 `margin: auto` で flex の伸長が効いていなかった | **「そういう演出か」と思ってしまう** |

`hidden` の件は特に気に入っている。

```css
/* これが無いと [hidden] が効かない */
[hidden] { display: none !important; }
```

`.btn { display: block }` は作者スタイルなので、ブラウザ既定の `[hidden] { display: none }` に勝ってしまう。**属性は立っているのに消えない。**

### コントラストの下限を2つに分けた

全組み合わせのコントラスト比を計算するスクリプトを書いたのだが、最初は全部に 4.5 を当てていた。すると**フォーカスの枠**が落ちた。

**枠は読むためのものではない。** 「そこに在ると分かる」ためのもので、WCAG でも非文字コントラストは 3:1 だ。

:::message
**4.5 を一律に当てると、足りているものを落として、表そのものが信用されなくなる。**
下限を「文字 4.5 / フォーカスの枠 3.0」の2つに分けた。
:::

分けたことで、逆に**本物の問題**が見えた。濃紺のバーの上のピンクの枠が **1.77** で沈んでいる。ヘッダーとフッターだけ枠が消えたように見えていた。濃い地の上だけ白い枠にして直した。

## まとめ

- **Jev は「分類」がそのまま要件になっている題材に強い。** 出力の形が崩れないので、パース周りの守りのコードが丸ごと要らなくなる
- ★ **出力の「性質」に要件が乗っているなら、UI より先にそこを測る。** ★ スキーマは型で守れるが、分布は型で守れない
- **題材に先行する権利があるなら、名前を決める前に調べる。** 調べた過程ごと残しておくと、あとで自分が助かる
- **制約が設計を良くすることがある。** 説明文を書き下ろす羽目になったおかげで、それがそのままモデルの判定基準になった

速さと安さは期待どおりだった。**300ms で返って、1回 0.02円に届かず、形式で落ちない。** if 文と LLM のあいだが埋まった感覚は、たしかにある。
